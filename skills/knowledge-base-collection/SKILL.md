# 知识库资料收集

## 核心原则

把外部资料加工成可长期复用的知识库条目，而不是只做内容摘要。每次处理都要保留来源、查重、判断是否值得入库、提炼可复用方法，并把文中出现的提示词、skills、插件、MCP、CLI、工具和链接单独抽取出来。

默认用中文说明；代码、命令、文件名、路径、链接保持原文或英文。只做与当前资料入库相关的最小改动。

## 适用场景

- 用户说“帮我记录这篇文章”“保存这个链接”“入库这篇资料”“整理这条 X”。
- 用户要求从文章里提取提示词、技能、MCP、CLI、插件、工具、命令、模型、链接或资源。
- 用户把网页、X 帖、公众号、官方文档、教程、视频文字稿等资料交给你，希望沉淀进 Obsidian/Markdown 知识库。
- 用户想把一次资料处理流程沉淀成任务卡、教程素材、提示词库条目或后续可复用 workflow。

不适用：用户只想临时问答、不需要保存到知识库；用户明确要求不要联网或不要改文件。

## 工作流

### 1. 先读本地规则

在目标知识库里优先读取相关说明和模板，常见文件包括：

- `AGENTS.md`
- `README.md`
- `链接文章索引.md`
- `链接文章入库边界.md`
- `保存后价值复盘.md`
- `链接文章入库模板.md`
- 与资料类型匹配的任务卡，如 `加工 X 文章为 Codex 知识卡.md`

遵守本地规则：修改前说明影响范围；只改相关文件；提交前运行最小验证；未知或可能很大的命令输出必须限量。

### 2. 获取资料正文

根据来源选择稳妥方式：

- 普通网页：优先浏览原链接；需要时抓取正文或元数据。
- X / Twitter：优先打开原链接；如果原文不可直接访问，可尝试公开嵌入、oEmbed、FxTwitter/VxTwitter 等辅助来源，并在笔记里说明来源。
- PDF / 文档 / 视频文字稿：按本地已有流程或对应技能处理。

不要把无法验证的内容写成事实。若只拿到标题或摘要，要标注“原文未完整抓取”，并询问用户是否提供正文或截图。

不要全文转载受版权保护的长文。知识库笔记应写结构化摘要、方法提炼和引用链接，短句引用要克制。

### 3. 查重

至少检查：

- 原始链接是否已在索引出现。
- 标题是否已存在。
- 作者、平台、主题是否已有近似内容。
- 是否是已有内容的转载、摘要或低质量重复。

查重结论用：`新资料` / `完全重复` / `近似重复` / `更高质量替代`。

### 4. 入库判断

按“主题边界 + 质量门槛”判断：

- 主题边界：是否属于当前知识库要收的范围。
- 质量门槛：是否至少满足 `原理`、`案例`、`应用` 中的两项。

入库决定用：`收录` / `不收录` / `合并到已有条目` / `暂存待判断`。

### 5. 新建或更新笔记

如果收录为独立笔记，建议结构：

```markdown
# 标题

## 来源信息
## 查重结果
## 边界判断
## 质量门槛
## 入库决定
## 结构化摘要
## 关键观点
## 可复用方法
## 文中出现的提示词、技能、插件、MCP、CLI
## 需要进一步验证的地方
## 保存后价值复盘
## 后续动作
## 相关页面
```

文件名优先使用：`YYYY-MM-DD 标题.md`。日期通常用资料发布日期；如果发布日期未知，用收集日期，并在来源信息中注明。

### 6. 必须抽取的资源清单

每篇资料都要单独检查这些类别，即使结果是“未明确出现”：

| 类别 | 抽取内容 |
| --- | --- |
| 提示词 | 可直接复制给 AI / Codex / Agent 的话术、任务描述、批注要求、系统指令片段 |
| AGENTS.md / 规则 | 长期行为约束、项目规则、自定义指令、操作边界 |
| Skills / 技能 | skill 名称、用途、安装方式、调用方式、创建方式 |
| 插件 / 工具 | plugin、connector、浏览器插件、Computer Use、截图、批注、预览等工具能力 |
| MCP | 明确出现的 MCP server、Model Context Protocol、MCP 工具名或连接方式 |
| CLI / 命令 | 命令行工具、安装命令、运行命令、参数、脚本入口 |
| 模型 / API | 模型名、API key、接口、额度、平台依赖 |
| 链接 / 资源 | 官方链接、参考文章、相关帖子、下载入口 |

推荐表格：

```markdown
## 文中出现的提示词、技能、插件、MCP、CLI

### 提示词 / 可直接复用的话术

| 类型 | 原文中的表达 | 可复用场景 |
| --- | --- | --- |

### AGENTS.md / 自定义指令

| 模块 | 核心要求 | 可沉淀用法 |
| --- | --- | --- |

### Skills / 技能

| 名称或概念 | 原文含义 | 备注 |
| --- | --- | --- |

### 插件 / 工具

| 名称 | 原文用途 | 备注 |
| --- | --- | --- |

### MCP

- 原文未明确出现 `MCP`、`Model Context Protocol` 或具体 MCP Server 名称。

### CLI

- 原文未明确出现 `CLI` 或具体命令行工具名称。
```

如果 MCP 或 CLI 没有出现，要明确写“原文未明确出现”，不要把相邻概念强行归类。

### 7. 更新索引

在索引表中新增或更新一行，至少包含：

- 日期
- 标题
- 原始链接
- 平台/作者
- 主题
- 分类
- 标签
- 查重结果
- 入库决定
- 保留复盘
- 保存位置

如果是重复资料，不新建笔记时也要在索引或原条目里留下“再次遇到”的记录，方便后续查重。

### 8. 最小验证

完成前至少验证：

- 新笔记文件存在。
- 原始链接能在笔记或索引中检索到。
- 索引保存位置指向正确笔记。
- Markdown 代码块成对闭合。
- 如果提取了 `MCP`、`CLI`、`skill`、`plugin` 等关键词，能检索到对应章节。

如果目录不是 git 仓库，直接说明无法使用 git 状态，不要伪造 diff。

## 常见错误

- 只总结文章，不提炼可复用方法。
- 把作者观点写成已验证事实。
- 忘记更新索引。
- 忘记抽取提示词、skills、插件、MCP、CLI。
- 没有区分“原文明确出现”和“可关联但未明确出现”。
- 为了保存资料而全文转载长文。
- 把一个低质量或无关链接直接收入主库，没有做边界和质量判断。

## 输出给用户

完成后简短说明：

- 新增或更新了哪些文件。
- 抽取了哪些资源类别。
- 做了哪些最小验证。
- 哪些事实仍需未来验证。
